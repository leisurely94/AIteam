## 1. 背景与问题

单人使用 AI 时，一次对话里要同时扮演需求方、架构师、开发、测试和评审，容易出现四类问题：

1. **目标没被说清就开始干活**：交付物跑偏，返工成本高。
2. **视角单一**：写代码的人自己评审自己，问题发现不了。
3. **上下文互相污染**：一本流水账，角色约束、评审意见、验收标准混在一起。
4. **过程不可追溯**：做完只剩一段聊天记录，谁在什么依据下产出了什么，事后无法复盘。

本项目把「一个人问 AI」改成「一个数字人团队协作」：用户只在主入口说清目标，系统自动组建带角色人设的数字人团队，按任务依赖推进、交叉评审，最后交回一份可追溯的交付包。

## 2. 产品目标

- **一句话起步**：主入口只需一段自然语言目标，系统负责澄清、拆解、组队、执行和汇总。
- **角色可感知**：每个数字人有姓名、职责、能力边界和产出风格，能看出「谁在做什么」。
- **像个真人同事**：每个数字人有独立形象、稳定口吻、可在主入口被点名多轮对话，并记住跨对话、跨项目的事实。
- **协作有闭环**：任务按依赖关系推进，关键产出必须经过独立评审角色，不通过则返工。
- **结果可交付**：一次运行产出一个目录：需求基线、团队名单、任务计划、各角色产物、评审记录、汇总报告。

### 非目标

- 不做通用低代码/工作流编排平台。
- 不内置真实工具执行器（不直接改库、发版、调用线上系统）。
- 不追求多租户、权限体系、计费；v0.1 定位是可在本地跑通的协作内核。

## 3. 目标用户与典型场景

| 用户 | 场景 | 期望 |
| --- | --- | --- |
| 团队负责人 | 接到一个模糊需求，先要方案和拆解 | 10 分钟内拿到需求基线 + 技术方案 + 测试计划 |
| 工程师 | 独立完成一个模块，缺评审 | 有架构角色定契约，有评审角色挑问题 |
| 质量同学 | 需要从目标直接推导验收标准与用例 | 验收标准与用例可对照、可执行 |
| 内容/运营 | 需要成体系的材料而非一段文案 | 多人分工产出后自动汇总成一份交付说明 |

## 4. 核心概念

- **主入口（Main Entry）**：唯一的对话入口，负责接收目标、提出澄清问题、组建团队、被点名与数字人对话、触发执行、交付结果。
- **数字人（Digital Human）**：具备**形象**（头像与名片）、**人格**（职责、能力、边界、表达风格）、**记忆**（跨运行的事实与偏好）、**对话能力**（多轮、上下文连贯）的执行单元。
- **数字人团队（Team）**：围绕本次目标组建的数字人集合，含一名 lead 负责统筹。
- **任务图（Task Graph）**：有向无环依赖图，每个任务绑定一个角色，产出物写入制品库。
- **评审闭环（Review Loop）**：独立评审角色对产出给出 pass/changes 结论，changes 触发定向返工，最多 N 轮。

## 5. 功能需求

### FR-1 目标接收与澄清

- 用户可在主入口以自然语言给出目标；系统生成 1–3 个只有用户能回答的关键问题（缺失的范围、约束、验收口径）。
- 澄清结果必须被吸收进需求基线，不得丢弃。
- **验收**：基线的 `goal/deliverables/constraints/acceptance` 字段完整；澄清回答中提到的约束出现在基线约束列表。

### FR-2 需求基线生成

- 输出结构化基线：目标、背景、交付物（3–6 条）、约束、验收标准（可验证）、待确认问题。
- 交付物与验收标准必须成对可对照。
- **验收**：基线为合法结构化数据；验收标准每条都能对应到一个交付物或任务。

### FR-3 数字人创建

- 依据基线与角色目录，选择完成本项目所需的**最小角色集合**，角色上限可配置。
- 每位数字人具备：姓名、角色、职责使命、能力标签、边界、表达风格、过程记忆。
- 必须包含 `product_manager`（基线/统筹）与 `reviewer`（独立评审）。
- 同一角色可实例化多名（如两名后端），需保证 id 唯一。
- **验收**：团队名单可导出为 `team.md` 卡片；lead 存在且在成员内；角色 key 全部合法。

### FR-4 任务计划生成

- 输出任务 DAG：任务 id、标题、角色、描述、交付物、依赖列表。
- 计划必须无环、依赖均存在、每个任务有负责人。
- **验收**：任务图通过校验器（无环、id 唯一、依赖合法）；每个任务都能追溯到基线中的交付物。

### FR-5 任务执行

- 按拓扑顺序执行；下游任务必须读到上游产物内容，而不是只拿到标题。
- 数字人执行时携带：角色人设、需求基线、本任务定义、上游产物、评审意见（返工时）、自身记忆。
- 单个任务失败自动重试一次；仍失败标记 `failed`，其下游标记 `blocked`，其余任务继续。
- **验收**：一次运行内所有 `pending` 任务要么 `done`，要么有明确失败/阻塞原因，不允许静默丢弃。

### FR-6 评审与返工

- 每个任务产物提交评审角色；评审输出 `verdict/issues/summary`。
- `changes` 时带着具体 issues 返工，返工轮数受上限约束（默认 1 轮）。
- 评审记录与轮次必须持久化。
- **验收**：评审意见可查；返工后的产物包含针对 issues 的补充内容；轮次不超上限。

### FR-7 汇总交付

- 生成汇总交付说明：结论、团队构成、任务与产物对照、验收对照、后续建议。
- 提供单文件导出，把汇总与各角色产物合并为一份可分发文档。
- **验收**：导出文件包含团队表、任务表与全部产物章节。

### FR-8 过程可追溯

- 运行数据落盘：基线、团队、计划、任务状态、消息（交接/评审）、事件日志、产物文件。
- 支持按运行 id 查询状态、查看进度。
- **验收**：`status` 能打印每个任务的状态与产物路径；事件日志按时间有序。

### FR-9 模型接入

- 支持 `mock`（离线规则，零依赖零密钥）、`ark`（火山方舟/豆包）、`openai` 兼容三类提供方。
- 模型不可用时不得整体崩溃：结构化步骤失败应回落到规则实现并留痕。
- **验收**：无密钥时 `mock` 可完整跑通全流程；真实模型接入只需配置环境变量。

### FR-10 数字人对话

- 用户可在主入口按姓名或角色点名某个数字人对话（`@林知远 ...`），也可用 `ai-team talk` 单独进入与某人的会话。
- 回复必须保持人设：称呼、判断口径、职责边界与该角色一致；不得越权回答其它角色的专业判断（可转交）。
- 多轮上下文连贯：连续追问时不重复自我介绍，能引用上一轮结论。
- **验收**：同一问题分别问产品与测试，回复的落点明显不同且都能引用本项目目标；连续 3 轮追问不出现人设漂移。

### FR-11 跨运行记忆

- 每个数字人拥有独立记忆库，记录用户明确表达的事实、偏好与项目约束。
- 记忆跨运行、跨项目保留；新会话开始时按相关度召回，而不是全量塞入上下文。
- 用户可查看与清空某人的记忆；写入记忆时给出可见提示，避免「偷偷记住」。
- **验收**：会话 A 中告知「周报要按周一到周五统计」，新开一次运行后询问统计口径，数字人能复述该约束；清空记忆后不再复述。

### FR-12 形象与名片

- 每个角色有固定的形象图与名片（姓名、角色、使命、能力、边界、口吻）。
- 团队名单在 Markdown 中可直接看到头像；运行目录内自带形象资源，离线和 GitHub 均可渲染。
- **验收**：`team.md` 中每个成员都有可显示的头像；`ai-team team` 能列出名片信息；缺少图片资源时不报错，降级为文字名片。

## 6. 非功能需求

- **零第三方依赖**：仅用 Python 标准库，降低接入与审计成本。
- **可离线验证**：无网络、无密钥即可跑出完整交付包（用于 CI 与演示）。
- **确定性**：`mock` 模式下同一目标产出稳定，便于回归测试。
- **数据本地化**：运行数据只写本地目录 `.ai_team/`，不上传任何外部服务。
- **可观测**：每个阶段有进度输出，事件写入 `events` 表与日志文件。

## 7. 主入口交互流程

```
用户 → 主入口：给出目标
主入口 → 用户：澄清问题（1–3 个，可跳过）
主入口：生成需求基线 → 组建团队 → 生成任务图
主入口 → 用户：展示团队名单（可选确认）
主入口：按依赖执行 → 评审 → 返工 → 汇总
主入口 → 用户：交付摘要 + 产物目录 + 单文件导出
```

非交互模式（脚本/CI）下跳过澄清与确认，使用保守默认值；交互模式（终端）下逐条提问。

## 8. 数据与产物

```
.ai_team/
├── memory/<human_id>.json   # 跨运行记忆：事实、偏好、最近会话
└── runs/<run_id>/
    ├── run.json           # 运行快照：基线/团队/任务/状态
    ├── state.db           # SQLite：runs/members/tasks/messages/events/artifacts
    ├── brief.md           # 需求基线（人读）
    ├── team.md            # 数字人名片（含头像）
    ├── plan.md            # 任务计划
    ├── final_report.md    # 汇总交付说明
    ├── assets/avatars/    # 形象资源副本（保证运行目录自包含）
    ├── artifacts/         # 各角色产物
    └── run.log            # 事件日志
```

## 10. 风险与待确认

- **目标歧义**：澄清问题质量依赖模型；`mock` 下使用固定问题模板，可能问不到关键点 → 提供 `--interactive` 由用户补充。
- **评审同源偏差**：评审角色与产出角色使用同一模型，可能互相「放水」→ 评审提示词强制对照验收标准逐条判定，并要求给出可执行 issues。
- **成本与限流**：真实模型下单次运行多次调用 → 任务数上限、产物截断长度均可配置。
- **角色冗余**：角色选多会稀释质量 → 角色上限默认 6，评审只保留一个。
- **人设漂移**：对话轮次变多后模型可能忘记角色约束 → 每轮重建人设系统提示，不放历史原始提示。
- **记忆污染**：误把一次性指令当成长期偏好 → 写入前区分「事实/偏好」与「本次任务要求」，后者不落记忆。
